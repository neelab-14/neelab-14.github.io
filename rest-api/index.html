Web の画面（JS）
スマホアプリ

【余談ネタ（時間があれば）】Blade の時代はバックエンドが主役で JS は画面を少し動かすオマケだった → API からデータをもらって JS で画面を組み立てる（SPA）時代になり JS のコード量が爆発 → 「フロントでこれだけ JS を書くなら、バックエンドも JS にして 1 言語にした方が効率よくね？」となって Node.js でバックエンドも JS に（Node.js 自体は 2009 年に「大量の接続を待つのが得意なサーバー」として生まれ、統一できるのは結果としての利点）→ 前後とも JS でコードが巨大化すると、型がゆるいので実行するまで間違いに気づけない → 書いている段階で型のズレを教えてくれる TypeScript（Microsoft、2012 年）でコード品質を上げよう、という流れ。 Laravel で Blade を返すのは「人向けの窓口（画面）」を作っていた。HTTP は使っているが、返事が HTML（画面）なので、プログラムが使う窓口（API）ではない。API にすると返事が JSON になり、Web・スマホ・他システムが同じ入口を使える。副作用：ログインはセッション（Cookie）からトークンへ、POST 後の redirect は 201 と JSON へ、画面は JS 側で描く。

やりたいことは「読む」だけ。読むだけなら状態を変えないメソッド GET を選ぶ（POST で取りに行くと「何か作るの？」と誤解されるし、キャッシュも効かない）。URL は「どのモノか」を表すので、動詞を入れず /users（ユーザーの集まり）の中の 42 番。合わせて「42 番のユーザーを、読む」＝ GET /users/42。

Q2
場面：ログインしていない人が、ブラウザのアドレス欄に直接 /api/users/42 と打って開こうとした
サーバーが返すべきステータスコードは？
→ 「ステータスコード」（4xx） のページ
401 Unauthorized

4xx は「クライアント側に原因がある」グループ。その中で 401 は「あなたが誰か分からない」＝ ログインしていない・トークンがない／期限切れ、のとき。名前は Unauthorized（認可されていない）だが、実際の意味は「未認証」なので注意。403 と迷いやすいが、403 は「誰かは分かっているが権限がない」で、まだログインすらしていないこの場面には合わない。

Q3
場面：一般ユーザーとしてログイン済みの人が、他人（43 番）の情報を GET /users/43 で見ようとした
サーバーが返すべきステータスコードは？
→ 「ステータスコード」（4xx） のページ
403 Forbidden

ログイン済みなので「誰か」は分かっている。分かっているのに見せられない、つまり権限がないのが 403。401（誰か分からない）とは「本人確認は済んでいるか」で区別する。認証（誰か確かめる）と認可（権限を確かめる）は別の段階で、401 は認証で失敗、403 は認可で失敗、と対応している。

Q4
場面：「登録」ボタンを押したら画面が固まったので、もう一度押した。裏では同じリクエストが 2 回飛んだ
POST /users だったら何が起きる？ PUT /users/42 だったら？
→ 「2 回送っても同じ？」 のページ
POST：2 件できる ／ PUT：1 件のまま

POST /users は「新しく作って、番号はサーバーが決めて」というお願い。2 回送れば、サーバーは 2 回とも新しい番号を振るので 2 件できる。一方 PUT /users/42 は「42 番をこの内容にして」というお願いで、対象を URL で指している。2 回送っても 42 番が同じ内容で上書きされるだけなので 1 件のまま。この「何回やっても結果が同じ」性質が冪等で、通信が途中で失敗したとき PUT は安全にやり直せるが、POST は二重登録の危険がある。

Q5
場面：先輩に「送っているリクエストの中身を全部見せて」と言われた
HTTP のリクエストは、何と何で出来ている？ 部品を全部言う
→ 「HTTP ＝ 1 往復」の一番下 のページ
メソッド・URL・ヘッダー・ボディ の 4 つ

HTTP のリクエストは、メソッド（何をしたいか：GET など）、URL（どこの何に対して）、ヘッダー（付属情報：形式・認証トークンなど）、ボディ（送るデータ本体。GET では通常なし）の 4 つで出来ている。REST はこの 4 つを「どう使うか」のルール集なので、この部品を言えることが以降すべての土台になる。レスポンス側はステータス・ヘッダー・ボディの 3 つ。

【操作】問題をクリックで答えと理由（1 問ずつ開く）。受講者に先に答えさせてから開き、理由を一緒に読む。全問、直前のページに答えが書いてある。

持ち帰る 5 つ

これだけ言えれば、面談で「REST を分かっている人」と伝わる。1 つずつ、自分の言葉で言い直してみる

1
REST ＝ HTTP を正しく使ってモノを操作するお作法
守らないと動かないルールではなく、守ると分かりやすくなる作法。だから守り具合に幅があり、よく守っているものを RESTful と呼ぶ
GET /users/42
2
URL は名詞、操作はメソッド、結果はステータス
この 3 点セットで実務の合格線（成熟度 Level 2）。URL に動詞を書かない、失敗を 200 で返さない
GET /todos → 200
3
ステートレスだからスケールする。認証は毎回トークンで
サーバーは前回を覚えない。必要な情報を毎回全部持って行くから、何台に増やしてもどれが受けても同じ
Authorization: Bearer …
4
他方式は REST の苦手への別解、または相棒
往復が多い → GraphQL、サーバー同士で速く → gRPC、サーバーから知らせる → WebSocket / Webhook。どれも上位互換ではない
GraphQL・gRPC・WebSocket・Webhook
5
迷ったら REST。理由があるときだけ他を足す
「REST を選ばない理由」がなければ REST。1 つのシステムの中で併用するのが普通。面談では必ず「要件次第」と前置き
